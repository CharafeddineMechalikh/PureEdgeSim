# Common benchmark specification (P1-CBS v1.0)

This document is the **single source of truth** for the cross-simulator
experiment. Each simulator reads these definitions through an adapter; no
simulator's own workload generator is authoritative. The JSON companion is
`crosssim/scenario.json`; the machine-readable application graph is
`crosssim/application_graph.json`; the shared arrival trace is generated by
`crosssim/common_trace.py` into `crosssim/traces/`.

Units: seconds, million instructions (MI), megabits per second (Mbps),
kilobytes (KB), metres. All timestamps are simulated time.

---

## 1. Three research objectives (kept distinct)

| Objective | Question | Evidence in this artifact |
|---|---|---|
| O1 Simulator calibration | Does temporal resolution distort measured orchestration outcomes? | PureEdgeSim clock/deadline/calibration grids; reproduced in YAFS, EdgeCloudSim, iFogSim2 where supported |
| O2 Cross-simulator validation | Does the phenomenon occur across simulation engines? | Common scenario on four platforms; capability matrix; scenario-equivalence records |
| O3 Application/infrastructure validation | Does it persist with dependencies and heterogeneous capacity? | Dependency-aware workflow arm, heterogeneous profiles, trace replay |

**O1 is not substituted for O2 or O3.** A Java/Python port of PureEdgeSim is a
cross-port audit, not a second simulator.

## 2. Research questions

* **RQ1** How does temporal resolution affect measured performance of multi-tier orchestration?
* **RQ2** Does that effect differ across simulators with different temporal semantics?
* **RQ3** How do application dependencies, workload mix and infrastructure heterogeneity change the effect?
* **RQ4** Are algorithm rankings stable across simulators, architectures and temporal configurations?
* **RQ5** What common calibration procedure makes results reproducible and comparable?

## 3. Application model (dependency-aware)

Scenario: **UAV-assisted surveillance and telemetry aggregation**. Three
workflow classes reuse the three calibrated task classes, so the original
independent-task results remain a special case of the new model.

### 3.1 Services

| ID | Service | MI | Input (KB) | Output (KB) | Allowed tiers | Notes |
|---|---|---|---|---|---|---|
| S1 | Data acquisition | 500 | 0 | 50 / 1500 / 900 | device, edge | produces raw sample; class-dependent size |
| S2 | Preprocess / decode | 600 (C1), 3000 (C2) | 50 / 1500 | 80 / 400 | device, edge | deterministic transform |
| S3 | Feature extraction / inference | 7000 (C2) | 400 | 120 | edge, cloud | the heavy service |
| S4 | Event detection / decision | 900 (C1), 1000 (C2) | 80 / 120 | 20 / 40 | device, edge, cloud | hard-deadline decision |
| S5 | Aggregation and notification | 19500 (C3), 500 (C2) | 20 / 40 | 200 | edge, cloud | long-deadline rollup |

### 3.2 Workflows (DAGs)

| Class | Workflow | End-to-end deadline | Total MI | Rate / device |
|---|---|---|---|---|
| C1 | S1 → S2 → S4 | 0.20 s | 2000 | 15 /min |
| C2 | S1 → S2 → S3 → S4 → S5 | 0.80 s | 12000 | 10 /min |
| C3 | S1 → S5 | 60 s | 20000 | 4 /min |

Edges carry the parent's output size as the child's input; a service placed on
a different tier pays the link cost on every edge. A workflow succeeds only if
**all** its services complete and the last service delivers before the
end-to-end deadline. Dependency violations and workflow-level completions are
first-class metrics.

**Two workload arms:**
* `independent`: the three classes are released as single tasks, matching the
  original P1 experiment (no dependencies).
* `workflow`: services are released as DAGs with the edges above; intermediate
  results are transferred explicitly. This arm tests O3.

## 4. Workload and arrivals

* Horizon **300 s**; warm-up 0 s for the reference configuration.
* Fleet **40 devices**: 40 % UAV (4 cores, 30,000 MIPS, 12 m/s), 40 % field
  (2 cores, 12,000 MIPS, 1.5 m/s), 20 % sensor (no compute, mobile=false).
* Class shares 35/35/30 % of devices; per-device rates 15/10/4 min⁻¹.
* Expected mix: C1 0.528, C2 0.352, C3 0.121 (1990 tasks in 300 s).
* The shared trace records `arrival_s, class, service, mi, input_kb,
  output_kb, deadline_s, workflow_id, predecessor_ids, device_id, seed`.
* All simulators consume the **same** trace; matching numerical seeds is not
  treated as equivalent to matching input.

## 5. Infrastructure and deployment

* Edge: 3 data centres × 16 cores × 80,000 MIPS, 32 GB RAM.
* Cloud: 1 data centre × 400 cores × 100,000 MIPS, 64 GB RAM.
* Links: Wi-Fi 300 Mbps / 10 ms; MAN 1000 Mbps / 10 ms; WAN 50 Mbps / 120 ms;
  Ethernet 1000 Mbps / 2 ms. Mist range 80 m, edge coverage 350 m, area 500×500 m.
* Orchestrator: global, at a designated edge node; collects node state at the
  control interval; decisions apply to all waiting tasks. (Document per
  simulator whether the native engine actually provides this.)

| Architecture | device/mist | edge | cloud |
|---|---|---|---|
| EDGE_ONLY | excluded | eligible | excluded |
| EDGE_AND_CLOUD | excluded | eligible | eligible |
| ALL | eligible | eligible | eligible |
| CLOUD_ONLY (reference, optional) | excluded | excluded | eligible |

The physical fleet is identical in every arm; only eligibility changes.

## 6. Temporal and factor settings

| Factor | Levels |
|---|---|
| Control interval | 1.0 s, 0.2 s, 0.05 s, event-driven (where supported) |
| Deadline scale | ×1, ×1.5, ×3, ×8, ×16 |
| Class mix | 5 controlled mixtures + trace-derived distribution |
| Architecture | 3 (+ optional cloud-only) |
| Infrastructure profile | uniform, edge_weak, edge_strong, split (full numeric spec in `scenario.json`) |
| Algorithm | random, round-robin, earliest-finish, least-loaded, deadline-aware, plus native algorithms as supplementary |
| Workload arm | independent, workflow |

## 7. Common metrics

| Metric | Definition | Boundary |
|---|---|---|
| Task completion ratio | completed / generated tasks | result delivered to source |
| Workflow completion ratio | complete DAGs / released DAGs | last service delivered |
| Deadline success ratio | jobs meeting end-to-end deadline | task or workflow |
| Scheduling delay | exec_start − dispatch | per task |
| Orchestration overhead | CPU/wall time of the decision routine | per decision |
| Resource utilisation | busy time / available time per tier | per node |
| Energy | idle + dynamic CPU + network, per task and per success | per node/link |
| Network usage | bytes and occupancy per link class | per link |
| Dependency violation ratio | DAGs with unmet predecessor or lost intermediate | per workflow |
| Simulation runtime | wall-clock, memory, events/s | per run |

## 8. Experimental unit and statistics

The experimental unit is the **seed-matched scenario run**, not a task. Tasks
within a run are repeated observations and are never treated as independent
replicates. Cross-simulator comparisons use the same trace and seed; simulator
identity enters as a fixed factor, with trace/seed as a random effect in a
mixed-effects model where supported. Holm correction is applied per declared
test family; effect sizes and bootstrap CIs accompany every p-value.

## 10. Status of this specification

Version 1.0 is the Phase-1 deliverable for reviewer agreement. Entries marked
`unavailable` in `CAPABILITIES.md` are facts established by implementation
attempts, not omissions. No cross-simulator result is reported until the
scenario-equivalence checks of Phase 3 pass.
